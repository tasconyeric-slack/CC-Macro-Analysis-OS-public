# Codex → verified Vercel PR previews

**Purpose:** Keep Vercel's `Require Verified Commits` enabled while making previews usable for Codex Cloud and local Codex.

## Automatic path (no signing key, PAT or new secret)

1. Codex pushes its work to a **same-repository** branch named `codex/<topic>` and opens or updates a PR targeting `main`.
2. `.github/workflows/codex-verified-preview.yml` runs as `pull_request_target` **from main**. It does not check out or run PR code; fork PRs and other branches are ignored.
3. If the current PR HEAD is already GitHub-verified, the workflow does nothing.
4. Otherwise it creates one GitHub-API commit whose **tree is byte-for-byte identical** to the current PR HEAD and whose parent is that HEAD. It omits author, committer and signature overrides so GitHub signs it using the existing `GITHUB_TOKEN`.
5. The workflow requires GitHub `verified=true`, `reason=valid`, the expected bot identity and the identical tree. Only then does it fast-forward the PR branch (never force-push).
6. It explicitly dispatches `checks.yml` on the new HEAD (GitHub Actions token-authored pushes do not automatically schedule ordinary CI). Vercel receives the GitHub push and can deploy the now-verified HEAD as a Preview.

**Important distinction:** the original Git commit generated by Codex remains unsigned. The workflow creates a **new verified checkpoint commit**, not a cryptographic signature on that original commit. This meets Vercel's HEAD verification gate without rewriting history, but it is **not** a claim that every ancestor commit is signed. It also does **not** certify code review or safety.

This process intentionally makes a zero-file-change commit, not a new research update. It does not modify immutable research artifacts, preregistrations, observations, the `main` branch or analyst decisions.

## Limitations and recovery

- Trigger: same-repo `codex/*` PR into `main`, on opened / synchronize / reopened / ready-for-review. If no PR exists, an unsigned Codex push may still display BLOCKED until a PR is opened.
- Race: a newer push during signing causes the stale job to exit; the newer PR synchronize event handles the new SHA. No force pushes.
- A BLOCKED deployment for the original unsigned SHA remains in historical deployment records; a new signed-SHA Preview should become READY.
- If a branch protection policy prohibits the non-forced update, this workflow will fail safely. Inspect the Actions log; do not disable Vercel's signature requirement.
- The ordinary PR CI triggers only on opened/reopened/ready-for-review to avoid GitHub-token-triggered synchronize runs being marked as failed or approval-required without jobs. Same-repository pushes run normal CI; signed checkpoints run CI through explicit workflow_dispatch. Fork PR updates after opening are not covered by this policy and must be reviewed separately if external contributions become relevant.
- If the CI dispatch is unavailable, the workflow signals failure after the signed HEAD was published. Re-run the checks manually from Actions, and fix the specific permission issue.
- No workflow can retroactively sign the unsigned original commit. For cryptographically signed original commits, use native Git SSH signing as below.

## Native signing for local Codex (optional; Git Bash)

On the workstation, **create and keep the private SSH signing key locally** (never put it into this repository or an agent prompt):

```bash
ssh-keygen -t ed25519 -f "$HOME/.ssh/id_ed25519_github_signing" -C "GitHub commit signing"
cat "$HOME/.ssh/id_ed25519_github_signing.pub"
```

In GitHub → Settings → SSH and GPG keys → New SSH key, register the **public** key with key type **Signing Key**. Then, from the local clone:

```bash
git config --local gpg.format ssh
git config --local user.signingkey "$HOME/.ssh/id_ed25519_github_signing"
git config --local commit.gpgsign true
git config --local --get user.email
```

The Git commit email must be an email verified on the GitHub account (or a matching GitHub-provided no-reply email). Check a newly signed commit using `git log -1 --show-signature`, push it, and confirm **Verified** on GitHub. Codex in that local clone inherits Git's signing configuration. A separate cloud Codex environment does not automatically inherit the workstation's private signing key; the trusted GitHub-API checkpoint remains the cloud fallback.

## Acceptance

A genuine *unsigned* same-repo Codex PR must get a subsequent GitHub-verified checkpoint commit and a Vercel Preview in READY state. A pre-verified Codex HEAD must cause no new checkpoint. The signed HEAD must receive a completed `checks.yml` workflow_dispatch run. Do not mark cloud fallback as fully validated until this real PR scenario has occurred.
