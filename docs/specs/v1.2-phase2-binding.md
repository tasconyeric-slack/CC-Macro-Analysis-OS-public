The approved contract is [`v1.2-phase2-research-contract.md`](v1.2-phase2-research-contract.md). This note
records how it binds to the existing code, and the few places where wording is adapted. No new
Observation, Evidence, Hypothesis or thesis engine is introduced.

## Where the wording is adapted

1. **10Y daily view (the one new metric).** The contract's A2 (20- and 60-trading-day changes) and D (20-day
   change) need daily 10Y yields, but Phase 1 stores `cn_cgb10y` deliberately as a month-end value. A2 is
   literally impossible from month-end rows.
   - *Missing capability:* trading-day changes of the 10Y yield.
   - *Required metric:* `cn_cgb10y_daily`, tier `supplemental`, `private_only`, frequency D.
   - *Why the P0 set cannot answer it:* the series is already fetched daily (same Wind code M0325687, same
     `rates` call) but only the month-end is stored.
   - *Information gain:* A2 and the bond leg of D become computable. No new Wind series, no extra call and
     no new code are involved. The dictionary declares `same_series_as: cn_cgb10y`; the adapter requests the
     code once and stores both views. The "one analytical concept per code" check still rejects any other
     reuse of a code.
2. **Request windows.** The Phase 1 windows were sized for Phase 1. The contracted windows need more
   history, so `wind_runtime.yaml` widens them: `rates` 70 → 130 days (61 trading days for the 60-day
   change), `credit` 430 → 500 days (15 monthly flows for the 3-month same-period comparison), and
   `property` 45 → 75 days (two 28-day windows). Still five calls; no code is added. The first real
   snapshot (2026-10-04) was taken with the old windows, so the diagnostics that need more history report
   `INSUFFICIENT_DATA` on it rather than being approximated.
3. **INSUFFICIENT_DATA on every assessment.** The contract lists R2 and R3 outputs without
   `INSUFFICIENT_DATA`; the general rule ("missing inputs do not silently become neutral") requires it, so
   every signal can return it.
4. **Three-valued assessments.** A missing input is never neutral: an assessment returns a class only when
   that class holds for every value the missing input could take. This is the same semantics the existing
   terminal rules use for `insufficient_data` leaves (`evidence.evaluate_condition`).
5. **R4 nominal premise.** The "apparent nominal improvement" leg is the preregistered monthly price tests
   alone (T-H1-01..03, at least 2 of 3). The external tests (T-H4-01..02, both) are reported as context for an
   external- or supply-led reading but never create the premise by themselves: H4 strength is not nominal-growth
   improvement. No preregistered production test exists, and adding one would be a new rule. (R4 v1 used
   price OR external; v2 corrected this before merge, as a new version because a v1 result was already
   stored privately.)
6. **C1 per city.** One definition (`C1_property_city_momentum`) yields one record per city
   (`C1_property_city_momentum.bj`, `.sh`, `.sz`, `.gz`). C2 requires all four cities.
7. **Consensus.** `X1_consensus_snapshot` records what was snapshotted and when, with no value-derived
   component, as `EXPERIMENTAL`. The loader refuses any other role while validation is `NOT_VALIDATED`.

## Preregistration check

No file under `research/cases/cn-nominal/preregistered/`, no evidence test, threshold, terminal rule,
hypothesis definition, probability or claim is changed. Phase 2 signals carry research roles
(CONFIRMATORY, CONTEXT_ONLY, COMPETING_EXPLANATION, EXPERIMENTAL); none is PRIMARY_EVIDENCE, and promoting
one would need a new prospective amendment.
