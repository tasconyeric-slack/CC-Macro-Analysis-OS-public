# V1.2.1 recommended implementation scope

> **Status: RECOMMENDATION, frozen with the Step 0 hardening change (2026-10-06). Updated 2026-10-06: the provider-neutral
> core (Order of work, step 2) is IMPLEMENTED (PR #9, see [design section 19](provider-independence-design.md#19-implementation-status-v121-core));
> no provider adapter is implemented and no route is activated.**
> Step 0 (operational hardening, [below](#step-0-pre-implementation-hardening)) is delivered by the change that adds
> these four documents. This plan follows from
> [`source-replacement-matrix.md`](source-replacement-matrix.md),
> [`provider-migration-priorities.md`](provider-migration-priorities.md) and
> [`provider-independence-design.md`](provider-independence-design.md). It was revised after an independent
> adversarial review, and again in a final correction pass (2026-10-06):
> - point-in-time route history;
> - the routing scope;
> - an access policy separate from semantic equivalence;
> - split semantic and activation gates;
> - multi-provider anchors;
> - a green baseline before any provider work.
>
> It changes no metric ID, signal formula, threshold, preregistered test or terminal rule. Wind support stays.

## Order of work

0. **Pre-implementation hardening: establish a green baseline.** Provider work does not start until this is done
   ([below](#step-0-pre-implementation-hardening)). It is a separate change, with its own review, before the provider
   refactor. A red baseline is not an acceptable V1.2.1 starting point.
1. **Human decisions** (listed at the end). None blocks the provider-neutral core. They gate **live collection** and
   **activation** of specific routes ([gate table](#route-gates-at-a-glance)), not the code.
2. **Provider-neutral core** ([design §18](provider-independence-design.md#18-smallest-change-set-for-v121-in-order),
   steps 1–5):
   - `SourceRoute`, `AccessPolicy` and `RouteChange`, for **routed metrics only**: those with a `wind:` contract or
     explicit `sources:`. Public metrics without `sources:` are untouched.
   - `route_at`, and the route-history rules: single-file validation at load, plus a mechanism that enforces
     cross-version append-only integrity. A loader reading one current YAML file cannot prove that history was never
     edited across Git commits, so the core change must supply that mechanism
     ([design §5](provider-independence-design.md#5-how-multiple-providers-for-one-metric-work-temporal-routing)).
     The ResearchRun retroactivity guard below is in addition to it, not a substitute.
   - The load-time gates: G1 semantic, G2 validation, G3 access, G5 boundary.
   - The Wind shim, which applies only when `metric.wind is not None`.
   - The provider-free signal eligibility rule (`signals.py:186-187`).
   - `normalize.py`, holding the shared month-end rule with its coverage guard, `validate_rows`, the drift checks,
     `publish(…, at)` (which splits rows into `observations/` and `candidates/`) and `select_active(obs, metrics, at)`.
   - Anchor discovery and eligibility; verified-only loading; the route filter at T before `as_of`, in `diagnose` and
     in the private `check` and `evaluate` paths.
   - `anchor` and `routes` in each ResearchRun; `routes` in `RUN_FIELDS`, with the legacy-genesis rule; the
     retroactivity guard.
   - `refresh-private --provider` with Wind opt-in; `diagnose-private --anchor` (`--snapshot` kept as an alias); the
     generic `runtime` manifest block.

   These tests must pass **before any adapter lands**: the golden swap, the late-retrieved provider, the temporal
   activation sequence, anchor ineligibility of candidates, the routing scope, and access fail-closed
   ([design §15](provider-independence-design.md#15-tests-that-would-show-substitution-does-not-change-signal-meaning)).
3. **The four Tier A replacements below, as candidates.** Each is one adapter with its tests.
   - Every route, EXACT ones included, starts as a candidate with `validation: PENDING`, and its history stays
     `[{genesis, wind}]`.
   - Live collection runs only where the route's access policy permits it. Otherwise only the parser and fixture
     tests land.
   - Activation is a separate, reviewed, time-stamped route-history record, appended only when that route's gates pass
     ([design §7](provider-independence-design.md#7-semantic-equivalence-and-activation-gates)). Files are never
     moved; candidate publications stay where they were written.
4. **Tier B groundwork, after sign-off on terms.** Beijing and Guangzhou candidate collectors, plus a Shenzhen
   reachability probe. No property route is activated in V1.2.1.

Provider keys use `[a-z0-9-]` only: `pboc`, `csindex`, `chinamoney-sdds`, `chinamoney-dr`, `tushare`, `bj-zjw`,
`gz-zfcj`. Publication files are named `<provider>_<run_id>.csv` and split on the first underscore.

## Step 0: pre-implementation hardening

**Reference platform.** The canonical V1.2.1 baseline is the **Linux GitHub Actions run on Python 3.14**, the platform
every workflow and the Netlify and Vercel builds use. At `main` 121874a it was green: **343 tests passed**, the engine
tests and the secrets/data-boundary check passed, and the Vercel production deployment for that commit was READY.

The "336 passed, 7 failed" result seen on the Windows workstation is **not** the repository baseline. It is
Windows-only portability debt: it does not show that the production test baseline was red. Step 0 fixes it where
practical, and does so by making the tests portable. It does not turn the Vercel/Linux build contract
(`scripts/vercel_build.sh`) into a Windows deployment script, and it does not weaken the Python 3.14 requirement.

**(a) Public-refresh workflow: the commit step failed on a clean `no_new_data` run.**
- **The failing command.** In `.github/workflows/refresh.yml`, "Commit new public artifacts" ran:

  ```text
  git add -A data/demo/observations research/cases/cn-nominal/refreshes research/cases/cn-nominal/updates research/cases/cn-nominal/eval
  ```

  It ran this before its "nothing to commit" check.
- **Why it failed.** On `main`, `research/cases/cn-nominal/refreshes/` and `.../updates/` do not exist and have no
  tracked files. A `no_new_data` refresh writes no record (`record: None`), so it does not create them either. Git
  then stops with `fatal: pathspec 'research/cases/cn-nominal/refreshes' did not match any files`, and the step
  exited non-zero instead of printing "No new public data; nothing to commit."
- **Evidence.** The latest scheduled `public data refresh` on `main` reproduced it exactly: `refresh-public` success,
  status `no_new_data`, secrets check success, then "Commit new public artifacts" failed with the fatal above. It was
  also reproduced locally with `git add -A --dry-run`.
- **Fix.** Least-privilege staging: only what a refresh writes. The rest of `research/cases/cn-nominal/` (`case.yaml`,
  `preregistered/**`, claims, presentation, memo templates and so on) is analyst-controlled, and an unattended job
  must not be able to auto-commit it. The append-only `refreshes/` and `updates/` directories are staged only if they
  exist, and no placeholder directories are created:

  ```text
  git add -A -- data/demo/observations research/cases/cn-nominal/eval
  for d in research/cases/cn-nominal/refreshes research/cases/cn-nominal/updates; do
    if [ -e "$d" ]; then git add -A -- "$d"; fi
  done
  ```

  A run with no new data still stages nothing, prints "No new public data; nothing to commit." and exits 0.
  `tests/test_refresh_workflow.py` runs the workflow's own staging script in the runner's shell
  (`bash -eo pipefail`) against a repository without `refreshes/` and `updates/`. It asserts the exact allowed output
  set: new observations, refresh records, update records and `eval/` changes are staged, while `refresh-summary.json`,
  `data/private/**` and edited, deleted or added analyst-controlled case files are not. It fails on the original
  command (the production error) and on a broad whole-case-root staging command.
- **What is not yet proven.** A local test is not proof that the scheduled workflow is fixed. The proof is a
  successful `workflow_dispatch` or scheduled `no_new_data` run on `main` after the change is merged.

**(b) The seven Windows-local failures.** The same tests pass on the Linux CI runner (343 passed). They failed only on
the Windows workstation, for these causes, each fixed at its root without changing production behaviour on Linux:

**Exit criteria for step 0.** Step 0 is finished only when every item below holds. The merge commit SHA and test
count are then recorded as the V1.2.1 baseline.
- **Tests.** Every pre-existing test passes on the reference platform (Linux CI, Python 3.14), and the full suite also
  passes on the Windows workstation. There is no skip, xfail or platform guard without a reviewed reason recorded in

- **Public refresh.** A clean `no_new_data` refresh exits 0, and its commit step reports "nothing to commit". Proved

- **Netlify and Vercel.** Builds still behave exactly as they do today.
- **Boundary.** `scripts/check_secrets.py` passes.

## Groundwork in V1.2.1 (not a replacement)

- **Beijing (`bj-zjw`) and Guangzhou (`gz-zfcj`) candidate collectors**, run daily by Task Scheduler. They start only
  after human sign-off on terms (question 5), recorded in each route's `access.basis`. Guangzhou forbids commercial use
  and mirroring; Beijing's terms are UNKNOWN.
  - Raw responses, with the per-use breakdown (住宅/商业/办公/车位; 期房 + 现房 for Beijing), are retained in each
    run directory.
  - Canonical rows under the *hypothesized* definition go to `data/private/candidates/`.
  - If review settles a different use filter, the rows are re-derived from the retained raw responses, with the
    original `retrieved_at`, into `candidates/`. That is allowed only before any activation
    ([design §5](provider-independence-design.md#5-how-multiple-providers-for-one-metric-work-temporal-routing)).
  - No signal reads these rows unless their route is active at the run's T.
- **Credit-free definition test.** Sum Wind's complete September 2026 daily values and compare them with each city's
  own monthly or YTD totals by use. This settles the use filter, but it cannot prove day-level identity.
- **Shenzhen.** A reachability probe from a mainland network, with no borrowed cookies or session.

## Unresolved questions requiring human judgment

1. **CFETS (gates DR007 and both 10Y views).** Request written permission from CFETS for low-frequency automated
   retrieval for private research. This is the recommended first step. If permission is not granted, the
   recommendation is to keep Wind active for these three views. An authorised structured provider would come in
   between, but none currently qualifies. Manual capture-and-import is documented, but its legal footing is
   unresolved, and it is **not** recommended. It would need an explicit recorded decision setting `manual_import` and
   `private_use` to `permitted`.
2. **TuShare tier.** Should we buy the 2000-point tier (about CNY 200/yr for an individual; 10× for an institution)? It
   would allow a DR007 overlap check and a practical CSI 300 fallback. It does not settle TuShare's own upstream
   licence for CFETS data, and it does not settle the use-status question.
3. **Use status.** CSI, TuShare's personal licence and Guangzhou permit non-commercial use only. Determine, with the
   reasoning recorded, whether this project's actual use qualifies. A work context or a public portfolio site is not
   assumed to be non-commercial. This gates CSI live collection and activation.
4. **Wind credits for 2026-10-13/14.** The X1 release-time validation needs Wind snapshots on those days. Restore
   credits for those few calls, or record that the validation slipped.
5. **Property terms and activation.** Sign off on daily automated collection from Beijing and Guangzhou. Accept a
   one-off Wind spend or export for the same-day comparison. Without it, those routes stay candidates.
6. **Loan-flow redistribution.** The source is PBOC data that the public demo already republishes in another form. Keep
   these four metrics `private_only` (recommended for V1.2.1), or review them later for reclassification?
7. **Shanghai property.** Choose a data agreement, manual entry, keeping Wind, or a three-city C2 as a new signal
   version under a prospective amendment.
8. **Consensus.** Keep X1 dormant (recommended), or commission a separate experimental consensus metric from a
   licensed panel under its own contract.
9. **Reference platform for the green baseline.** *Decided 2026-10-06.* The canonical baseline is the Linux GitHub
   Actions run on Python 3.14. Windows-local failures are portability debt, fixed where practical in Step 0 by making
   the tests portable. They are not evidence that the production test baseline was red.
